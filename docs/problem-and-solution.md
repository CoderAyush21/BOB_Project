# Problem & solution statement

## Problem

Every engineering team fixes bugs, and many of those bugs come back.

- **Fixes ship without regression tests.** Under incident pressure the fix goes out, and "add a test" becomes a postmortem follow-up nobody finishes. When someone later refactors that code, nothing stops the bug from returning.
- **The same mistake gets written again in new code.** The engineer who writes a new module never saw last spring's incident. The pattern (a missing null guard, float money math, an off-by-one) reappears somewhere else.
- **Current tools can't see this risk.** Coverage says "80% of lines executed," not "would our tests catch the bugs we've already shipped?" Classic mutation testing generates thousands of random mutants, which is too slow and noisy for most teams to adopt.

The cost is high because a regression means paying for the same bug twice: another incident, another investigation, and lost customer trust ("you already fixed this!").

## Solution: Bug Vaccine

Bug Vaccine turns a repository's own history into a vaccine, using IBM Bob 2.0 to handle the parts that need understanding:

1. **Mine**: collect every bug-fix commit and incident postmortem from the repo.
2. **Extract antigens** *(Bob, document understanding)*: identify the reusable pattern behind each bug, and flag postmortem follow-ups that were never done.
3. **Hunt** *(Bob, parallel subagents)*: one subagent per pattern searches today's code for every place the bug could recur, including code written after the fix.
4. **Re-infect**: inject each historical bug one at a time and run the test suite. Caught = immune. Not caught = the bug could come back unnoticed.
5. **Antibodies** *(Bob, Agent mode)*: write tests that guard each bug *pattern* (many inputs, every affected function), then iterate until all known mutants are caught.
6. **Prove**: re-run, then check against **held-out mutants**, new variants generated by a separate subagent that never saw the antibodies. This shows the tests generalise rather than memorise.
7. **PR mode** *(code review)*: on every pull request, check only the changed files and post a comment when new code repeats a bug the repo has already shipped.

## Impact (measured on the sample project)

| Metric | Before | After |
|---|---|---|
| Past bugs caught if re-introduced (known mutants) | 2 / 6 (33%) | 6 / 6 (100%) |
| Held-out mutants caught (variants the antibodies weren't written against) | — | 6 / 6 (100%)* |
| Postmortem #57 follow-ups completed | 0 / 2 | 2 / 2 (regression test added; nested-field audit done by the hunt) |
| Antibody tests added | — | 6 (production code untouched) |
| Time for one re-check (tool steps only: baseline + 6 mutants) | — | ~4.5 s with `node --test` (~11 s through `npm test`) |
| Risks flagged in PR #88 before merge | — | 5: three new lines that repeat known bugs, two past-bug sites with no test |

\* *Prototype caveat:* in the prototype, the antibodies were revised after an earlier, mutant-specific version scored only **50%** on the held-out set. That result is exactly what the held-out check is for, and it led to the "guard the pattern" rule in `bob-prompts/03-vaccinate.md`. In the Bob run, the held-out set is generated only after the antibodies are final, so the score is blind.

The #57 incident itself shows the cost of one regression in this sample project: a SEV-2, a 3h 10m outage, and 312 invoices delayed.

Two findings a human reviewer would likely miss:
- The #57 fix shipped without a test. Its postmortem says to add one, and it never happened. Reverting the fix goes completely unnoticed.
- A module written *after* all three fixes repeats **all three** historical bug patterns, and its tests catch none of them.
